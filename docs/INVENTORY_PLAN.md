# Inventory and shopping lists — implementation plan

Status: v4, 2026-11-19 — v3 plus the corrections of review round 4 and the owner's decisions of that day. Design: `docs/INVENTORY_DESIGN.md` (v5). Mockups: a private design canvas held by the owner, approved. No code exists. Stage names such as L3-11 refer to the deploy gate, which lives in the infra repo.

Two earlier versions of this plan were judged unsound by review. This one follows a design that was simplified instead of patched, and was judged sound with corrections; the corrections are applied and not yet reviewed. "Review status" at the end says exactly what that covers; read it before starting.

## Ground rules

- **No user-visible change reaches prod before phase 9.** Schema is the exception, and not an optional one: every schema change ships dark to the main branch and prod before the feature branch creates rows of that shape on dev (brief, gate point 4). That applies to phase 1 and to any later migration.
- **Tests ship in the same commit as the code they cover.** The gate's rule is satisfied by any test file, so it is not enough: each phase names the tests it must add and where they live.
- **Every phase ends with an independent adversarial review**: findings re-read in the code before acting, then re-test. Corrections get reviewed too; three times already a correction was the defect.
- **A phase is finished only when its scenarios pass where they run**: API tests, unit tests, Playwright against dev, desktop Brave, and the physical Android phone over adb. A check goes to the owner only when it cannot be driven.
- **Do not build on an unmeasured item.** Every platform claim is either cited in the design brief or listed in phase 0.
- **The feature is dark by default.** `inventory_view` is false on every project; the sidebar entry and the widget render only when the viewer can see a project with inventory on; `/shopping/` says so when there is none.
- **Do not add rules to the operations.** The design has two behaviours on purpose. A case they do not cover is either an accepted behaviour written into the brief or a question for the person holding the phone, not a third behaviour.
- **No new keys in `packages/i18n`.** Strings come from dictionaries (en, es, pl) local to the inventory code.
- **Migrations are generated by `makemigrations`, never hand-written**, and `makemigrations --check --dry-run` must be clean after every model change.
- **The gate is shared by every ref.** See "Gate changes".

## Architecture in one paragraph

A Django engine applies operations to project-scoped inventory models and derives one to-buy list per viewer. A small standalone app at `/shopping/` serves the phone (own manifest, own service worker, IndexedDB queue, "Done" kept on the device). Surfaces inside the main app (sidebar entry, Home widget, project page) call the same endpoints online with no queue. Both UIs share one pure-TypeScript package. An MCP server calls the same endpoints.

| Thing | Location | Why there |
|---|---|---|
| Models, engine, views | `apps/api/plane/...` | fork code; triggers the tests-with-change rule |
| API tests | `apps/api/plane/tests/unit` and `.../contract` | the only two directories the API stage runs |
| Shared derivation fixture | `apps/api/plane/tests/fixtures/inventory/` | the API test container mounts only `apps/api`; the TypeScript tests read it by relative path from a full checkout |
| Shared package | `packages/inventory`, tests in `packages/inventory/tests/` | matched by the rule's `packages/*/tests/` pattern; added to the unit stage's list |
| Standalone app source | `packages/shopping-app`, tests in `packages/shopping-app/tests/` | same |

## Working loop

- API: the pytest suite runs locally in docker. A test that asserts a schema property must be proven with `--create-db`, because the default reuses the database.
- Web unit tests run on the gate's runner from a pushed commit; `tsc`, `oxlint` and `oxfmt` run locally on the files touched.
- Fast UI loop for the standalone app: its Vite dev server in a container on the workstation, proxying `/api` to dev with an injected API key, reached from the phone with `adb reverse`. It proves layout and interaction only. Known distortions: every operation is recorded as coming from the API, the per-key rate limit applies, each request writes an activity-log row, the key must belong to a QA-domain user, and every gate run reseeds QA users and kills the key.
- Honest loop: a dev-only deploy of the branch (the only place the image build is exercised), then the scenarios in desktop Brave and on the phone.

## Phase 1 — schema and flag

- Models in `apps/api/plane/db/models/inventory.py`: list, item, order, preference on the project and workspace base models; the event table as a plain model with no soft delete and nothing depending on it. Foreign keys `CASCADE` to parents and `SET_NULL` to users; never `DO_NOTHING`, never `PROTECT`. Check constraints: `min_quantity ≥ 0`, `restock_to` empty or `≥ min_quantity`. **No constraint on `quantity`**: it is signed on purpose. Unique: `client_op_id` on events; a list's live items by normalised name.
- `inventory_view` on `Project` with `default=False, db_default=False` (M7), in the lite list's `.values(...)` and in the external serializer. No endpoints yet.
- `shopping` added to both restricted-name lists, after checking no workspace has that name.
- Tests: constraints with `--create-db`; `makemigrations --check` clean; an `INSERT` into the projects table that omits `inventory_view` succeeds (what an older image does after a rollback), proven with `--create-db` and again on dev's real database after the migration; the lite list and both serializers return the flag; a workspace cannot be created with the name `shopping`; the hard-delete task and the QA seed's reset run over a workspace holding lists, items, orders and events, completing with no integrity error and no rows left.
- Exit: M7's answer applied; this phase merged to the main branch and deployed to prod through the normal gate, dark, **before** phase 2 creates any inventory row on dev.
- The owner agreed to that prod deploy on one condition: the service keeps working. Made concrete:
  - not before M6 and M7 are answered and the rollback has been rehearsed on dev;
  - the change is additive only — new tables, one new column with a default, one reserved name — and touches no existing query except the lite project list;
  - the normal gate, with nothing skipped; any red stops it, and the prod smoke rolls back by itself;
  - afterwards, checked by hand and recorded: sign-in, opening a project, creating and deleting a project, creating a work item, and the next night's hard-delete task finishing without an error;
  - if any of those fails, roll back first and investigate after.

## Phase 2 — engine and API

- An engine module with no HTTP in it; views stay thin.
- The visibility rule written once and used by the to-buy list, the counter and the suggestions.
- `ops/`: at most 100 operations per request, array order, **one database transaction per operation** with a row lock on the item and database-side arithmetic; authorisation against the item's current project; the two behaviours exactly as the brief states them — always-applies for adjust, buy, mark ordered, arrived and cancel (the last two against the order's status), and compare-and-set on `base_rev` with the same-queue exemption for set level, set needed, pin, change mode and recount; revert compared against the revision its operation produced; results applied, stale, rejected; the ledger returning recorded results for duplicates; unknown format versions rejected.
- The exemption requires the same person and the same `queue_id`. Authorisation runs before the duplicate lookup.
- Orders with their three transitions and an id supplied by the device; the overdue flag and the "bought since it was ordered" mark computed on the server. Order actions cannot be reverted.
- Endpoints: `shopping-list/`, `ops/`, `suggestions/`, `preferences/`, and project-level create, update and delete of lists and items.
- The item update endpoint accepts data fields only and does not advance the revision. Creation refuses a duplicate name in the list and returns the existing item.
- Event pruning after 90 days as a scheduled task.
- Guests answered with 403 on every endpoint. The per-key rate limit added to every inventory view; API-key requests recorded with source `api`.
- Tests:
  - every operation × every mode, table-driven;
  - compare-and-set, the same-queue exemption and its negative case, revert in each form, duplicates of every result kind;
  - the authorisation matrix on every endpoint and on `ops/` with a valid foreign item id: admin, member, guest, non-member, deactivated member, archived project, soft-deleted project, soft-deleted list, flag off, another workspace's item;
  - leak tests on the to-buy list and on suggestions: secret project, public project another member can join, two viewers;
  - the two-person scenarios of the catalogue, each a named test issuing the calls in the stated order;
  - **real overlap**, with real transactions and two connections: two deltas, two statements, the same operation twice, two batches touching the same two items in opposite order;
  - **a randomized test**: generated histories of two people, each with a phone queue and a queueless surface (widget or MCP), plus two people sharing one phone, with offline periods, delivered in every order the queues allow, checked against invariants (a delivered purchase is never lost; no operation takes effect twice; `units` totals do not depend on delivery order; a statement never overwrites a change its author had not seen);
  - time with a frozen clock: negative and oversized ages, "bought N days ago" across a day boundary and a DST change in Europe/Warsaw;
  - a batch mixing good operations with a deleted item, a forbidden item and an invalid-for-mode one;
  - a query-count budget for the to-buy list with 500 items.
- Exit: suite green locally and on the runner; review of the engine.

## Phase 3 — shared package

- `packages/inventory`: types; derivation; the operation builder (`v`, `client_op_id`, `queue_id`, `base_rev` captured at the tap, the tap time stored so `age_ms` can be computed when sending); a pure queue reducer — strict first-in-first-out; each entry marked never-transmitted, transmitted or answered; optimistic apply; reconcile with results; retry with the same ids and backoff; nothing reordered or dropped by itself; undo by removal only for a never-transmitted entry and by a queued revert otherwise; entries older than two hours held, blocking everything behind them; entries older than 60 days discard-only; "apply anyway" as a new operation for `stale` only; a blocked queue the user can unblock by discarding its first entry; a discard taking its reverts with it and its row out of "Done"; another user's queue left alone; a `queue_id` per install and user; storage schema version; the API client (JSON only, `redirect: "manual"`, M4's definition of "not delivered"); one replay at a time per device.
- One derivation fixture file under `apps/api/plane/tests/fixtures/inventory/`, read by the API tests and by this package's tests.
- Tests: the fixture; the reducer against the catalogue's expected outcomes; **a randomized test of the reducer against a small model of the server**, generating lost answers, restarts, holds, discards and undos at every point in an entry's life, with the invariant that what the device shows equals what the model server holds once the queue is empty; a queue written by storage version n read by n+1 and by n+2; two replays started at once deliver each operation once.
- Gate: the package joins the unit stage's list and defines `check:types`.
- Exit: the unit stage's output names the package's tests as run.

## Phase 6 — offline

- IndexedDB: last snapshot, the per-user queue, storage version, the "Done" list. Optimistic apply, replay on reconnect, the two-hour hold, the waiting-and-unapplied screen.
- Service worker scoped to `/shopping/`: precached shell and assets, versioned cache, an update path that never drops queued operations. **Precache rejects any response whose content type does not match the file asked for** (M1: a missing file answers 200 with the main app's HTML), and the install fails rather than caching it. Manifest and icons. `storage.persist()`.
- Sending (M10): a one-off background sync on every enqueue, which fires within seconds of the network returning while the browser is alive; and a flush on every open, on the `online` event and on focus, because after a force-stop nothing fires until the browser starts again. The list header shows how many changes are waiting, at all times.
- Offline, the app refuses what needs a connection (creating an item, editing its data) with a clear message.
- Tests: Playwright on Chromium with `setOffline` for tick, level, ±, recount, needed, pin, order, arrival and cancel offline, then reconnect; undo of an entry that was sent and not answered; a held entry blocking the fresh ones behind it; `stale` results surfacing; a 5xx, a sign-in page and a response dropped after the server applied, then a normal delivery; a queue older than two hours held and then sent or discarded; session expired during replay; another user signing in; an app update with a non-empty queue; two tabs replaying; reload while offline; the worker's registered scope read at runtime. On the phone: the same in real airplane mode, cold start from the icon, and tap-offline, kill the app, restore the network, reopen.
- Gate: the worker check; the guest and crawl additions to the smoke.
- Exit: offline scenarios pass on the phone; review of worker, queue and gate changes together.

## Phase 9 — full matrix, rehearsal, prod

1. The whole scenario catalogue on dev, in desktop Brave and on the phone, until every row passes.
2. Rehearsal on dev of the prod rollout and of a rollback, reading the gate after each step.
3. Review of the complete diff; findings verified; re-test.

## Gate changes

A check must not learn from the thing it checks whether to run. **Expectation** — "this image should contain the feature" — is derived from the tag of the image under test: the tag is the commit it was built from, and that commit's tree either has the shopping package or does not. It is not stored: the deployed-ref marker is written after the checks that would need it and deleted by a rollback, so a stored value would always describe the previous deploy. When the feature is expected, every check below is mandatory.

## Risks

- **The rules for concurrent changes were wrong three times.** v4 answers with fewer rules, not better ones. If phase 2's randomized test or a review still finds a wrong outcome, the fix is to hand that case to the user or to write it down as accepted, not to add a rule.
- **A second icon may not be installable from one origin (M2).** Fallback: a shortcut on the existing icon; the rest is unchanged.
- **Two UIs.** The standalone app duplicates presentation, not logic.
- **Once inventory rows exist in prod, rolling prod back to an image from before phase 1 is not available** (M6): L3-16 turns red and purges of workspaces or projects with inventory rows fail. Fixes go forward.
- **Dev, the runner and the QA data are shared with every other deploy.** Shipping the schema dark first and the separate QA workspace exist for this; M6 and M12 have to confirm both.
- **The phone's browser may kill the worker or evict storage** in ways only the device shows (M3, M9, M10). It is a canary build: its behaviour can change from one week to the next, on three phones that update separately.
- **The fork carries more to rebase**, concentrated in new files; the edits to upstream files are the flag plumbing, one insertion in the sidebar, and the widget.

## Decisions

Taken by the owner on 2026-11-19:

1. Ticks apply at once instead of at "Finish shopping"; "Done" is kept on each device.
2. Without coverage: shop and capture, not create or edit — and what was done offline must be sent by itself when the connection returns (M10 decides how far that reaches with the app closed).
3. Changes older than two hours ask before being sent. Clarified in phase 9: every change not yet answered, including one whose attempt failed without network (it had been exempt).
4. A purchase always counts when it syncs, whatever was said about the item before.
5. A recount does not know about changes waiting on the other phone. When the two shop together without coverage they talk; not a problem.
6. Guests get no access, and only a project's members see that project's lists.
7. Phone screens as a standalone app at `/shopping/`.

Not objected to, and not asked one by one: categories and stores as free text with the aisle order per person; a need flagged on an item already on order being cleared on arrival; a wrong phone clock only affecting shown times; photo last.

8. The app is installed from both hostnames if that is possible, otherwise from the public one only (M11). The owner chose this knowing that two installs are two separate apps, each with its own waiting changes and its own "Done".
9. The empty inventory tables go to the main branch and prod in phase 1, **provided the service keeps working** (phase 1 says what that means).
10. The mockups are approved as they stand.
11. The corrections made after review round 4 are not reviewed on paper again; each is reviewed when the phase that builds it is reviewed.
12. Both real phones use Edge Canary.

Later, outside this plan: a native Android app, once everything here is finished. Nothing in this plan builds towards it, but the API the standalone app uses is the one a native client would call.

Why 9 was not a free choice: the inventory tables, empty and unused, go to the main branch and prod in phase 1, and so does any later change to them. The gate's QA seed and the purge delete through Django, and an image that does not know the inventory models cannot delete a workspace that holds inventory rows, so otherwise every unrelated deploy fails once the feature branch has run on dev. The only alternative is to deploy nothing else while this is built.
